Architecture · SOVD gateway · IAM

One gateway, many SOVD servers, down-scoped tokens

1Tester gets an IAM tokenOIDC sign-in (authorization code + PKCE, MFA). The IAM token is limited to this vehicle (audience = VIN) and carries the technician's role as scopes. The tester's device certificate comes from the OEM PKI.
2One external entry pointThe tester only ever talks to the SOVD Gateway, over HTTPS with mutual TLS. Guest SOVD servers and the CDA can't be reached from outside, and raw UDS/DoIP is blocked at the vehicle edge.
3Verify, decide, exchangeThe gateway checks the IAM token's signature against JWKS keys anchored in the TEE, plus expiry, audience and revocation. It then applies policy (role → entity → resource, locks, vehicle state) and mints a down-scoped token in RFC 8693 token-exchange style. The TEE signs it, so the signing key never sits in Linux.
4Down-scoped tokenThe token's audience is one server (VM 1, VM 2 or the CDA), its scope covers only the requested resource, and it lives seconds to minutes. It can be bound to the gateway's mTLS certificate (RFC 8705). Each server checks the gateway's signature, its own audience and the scope, then applies its own local authorization as defence in depth.
5CDA as a SOVD serverThe CDA exposes classic ECUs as SOVD entities. It translates to UDS with the ODX description, connects over DoIP with TLS, and authenticates to each ECU with 0x29. The TEE signs the challenge, and only for an ECU and security level the scoped token allows.
—TraceabilityThe gateway logs the technician's identity (sub from the IAM token) against the exchanged token's jti, so every action on any server traces back to one person. Logs go to the VSOC.
