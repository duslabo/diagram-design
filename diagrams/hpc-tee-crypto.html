Architecture · Arm TrustZone + OP-TEE

How a guest VM reaches the TEE to run crypto

1Client App → driverTEEC_InitializeContext, TEEC_OpenSession (TA UUID), then TEEC_InvokeCommand. Buffers go through TEEC_RegisterSharedMemory. libteec turns each call into ioctl(TEE_IOC_INVOKE) on /dev/tee0.
2Driver builds the messageThe guest TEE subsystem packs an optee_msg_arg. Shared-memory references in it are still guest addresses (IPAs).
3avirtio-tee pathThe frontend puts the request and the shared-memory page list on a virtqueue and kicks. The VMM backend (QEMU or a vhost-user daemon) maps guest memory and receives the request.
3bTrapped-SMC pathAlternative with no virtio: the guest driver issues an SMC itself, EL2 traps it (HCR_EL2.TSC), and the in-hypervisor mediator handles it. This is how Xen's OP-TEE mediator works.
4Mediator (the control point)Checks the call, translates IPA → PA through the stage-2 tables, pins shared pages, and puts the guest's VMID in the SMCCC client-ID register (w7). It also tells OP-TEE when VMs start and stop (OPTEE_SMC_VM_CREATED / _DESTROYED).
5SMC to EL3TF-A's SMCCC dispatcher (the OP-TEE dispatcher, opteed) saves normal-world state and switches the CPU to the secure world.
6OP-TEE selects the guestBuilt with CFG_NS_VIRTUALIZATION, OP-TEE keeps a separate partition for each VMID (its own heap, sessions and shared memory), so guests can't see each other.
7–8Crypto TA runsTA_InvokeCommandEntryPoint runs the operation through the GP Internal Core API: TEE_AllocateOperation, TEE_AEInit/TEE_CipherInit, TEE_AsymmetricSignDigest. Keys live in secure-storage objects (TEE_OpenPersistentObject).
9HardwareOP-TEE's crypto layer either calls an accelerator driver or uses its software library. Secure storage is encrypted with keys derived from the hardware unique key (HUK). The result returns along the same path, and TEEC_InvokeCommand returns a TEEC_Result.
