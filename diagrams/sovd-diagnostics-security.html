Architecture · SOVD + CDA · Security

Secure remote diagnostics: SOVD to the HPC, UDS to the ECUs

1Tester signs inThe technician signs in to the OEM IAM with OIDC (authorization code + PKCE) and MFA. Their identity is tied to a tester device certificate from the OEM PKI.
2Short-lived tokenIAM returns a JWT access token with the technician's role mapped to SOVD scopes (e.g. read faults, run routines, flash). The audience is limited to the VIN and the lifetime is minutes, not days.
3SOVD over mutual TLSREST calls (ISO 17978) go over HTTPS with mutual TLS: the tester's client certificate and the vehicle's server certificate, both from the OEM PKI. The token rides in Authorization: Bearer.
4Access policy (the gate)Checks the JWT signature against cached JWKS keys and checks expiry, audience and revocation. It then maps scope to resource (/components/{id}/faults, /operations, /data), takes an exclusive lock and checks vehicle state, e.g. speed 0 before flashing. Anything not allowed gets a 403.
5DispatchThe SOVD server answers HPC-native entities itself and sends requests for classic ECUs to the CDA as a job.
6CDA → ECU over DoIPThe CDA translates SOVD to UDS using the ODX description, connects over DoIP with TLS (ISO 13400, port 3496) and authenticates to the ECU itself: UDS 0x29 certificate authentication, or legacy 0x27 seed/key with keys held in the HPC's HSM. The tester never holds ECU keys.
7Into the mechatronic layerThe zonal gateway's diagnostic firewall allows only expected source addresses and services, then routes to CAN-FD ECUs. SecOC protects those frames against spoofing and replay.
—Audit and blocked pathsEvery request, policy decision and denial is logged and sent to the VSOC (vehicle security operations centre). Raw UDS/DoIP from outside is rejected at the vehicle edge: the external port exposes only SOVD.
