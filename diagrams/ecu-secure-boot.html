Architecture · HSM-based ECU secure boot

Secure flashing and secure boot on a classic ECU

ASecure flashing startsThe CDA on the HPC, holding a scoped token, opens a programming session (0x10 02), authenticates with 0x29 or 0x27, and downloads the image with 0x34/0x36/0x37.
BImage lands in flashThe bootloader writes the application and calibration data along with a signed header: version, hash, and an ECDSA signature from the OEM application key, which chains to the OEM root key.
CVerify before marking validIn the 0x31 check routine, the bootloader asks the HSM to verify the signature against the root key in OTP and to check that the version isn't older than the anti-rollback counter. On success the HSM stores a fast CMAC reference, raises the counter and marks the image valid.
1HSM boots firstThe HSM ROM verifies the HSM firmware, then checks the bootloader against its stored CMAC. Only then does it release the host core from reset.
2Application checkThe HSM checks the application and calibration data against their CMAC references. If boot time is tight, this runs in parallel while the bootloader starts.
3Jump only if validThe bootloader jumps to the application only if the image is marked valid and the HSM check passed. Otherwise it stays in the bootloader so the ECU can still be reflashed.
4Keys follow a valid bootThe HSM releases SecOC keys to the application only after a successful verified boot (the SHE boot-protection idea). A tampered ECU can't sign messages, so its peers drop them.
✕Failure reactionUnsigned or old software is never activated. On failure: stay in the bootloader or limp home, keep the keys locked, and have the IDS manager report a security event to the HPC's IdsR and on to the VSOC. The bootloader flash is write-protected and debug is locked after production.
